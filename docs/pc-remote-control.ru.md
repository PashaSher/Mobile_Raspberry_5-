# Управление роботом с ПК по Wi‑Fi (не прошивка Romeo)

На Raspberry Pi программа `send --listen` делает две вещи:

1. **Видео** — один TCP‑порт (MJPEG), как раньше.
2. **Команды Romeo** — отдельный TCP‑порт; всё, что приходит с ПК по этому порту, Pi пересылает на USB `/dev/ttyACM*` как текстовые строки (плюс опциональный JSON → те же команды).

Ниже — как встроить это в приложение на Windows/Linux/macOS.

---

## 1. Узнать адрес и порты Pi

### Вариант A: UDP discovery (как у вашего приёмника видео)

- Шлёте на broadcast UDP запрос с тем же портом и форматом, что уже использует ваш клиент для поиска Pi (поле `cmd: discover` и т.д.).
- В ответе от Pi в JSON есть минимум:
  - **`tcp`** — порт **видеострима**;
  - **`control`** — порт **управления** (если на Pi не отключали `--romeo-control-port 0`).

Сохраните `ip` отправителя ответа, подключайтесь к `ip:tcp` для картинки и к `ip:control` для команд.

### Вариант B: без discovery

- Задаёте IP Pi вручную (например `192.168.1.50`).
- Порт видео — тот, что задан на Pi (`send --listen --port 5000` → обычно **5000**).
- Порт управления по умолчанию **5001** (`--romeo-control-port`), если не меняли.

## Видео с Pi: формат потока (совместимость с приёмником)

Передаётся **не** «сырой» MJPEG по HTTP (`multipart/x-mixed-replace`), а **TCP‑поток со своей рамкой**:

1. Подключение: **`TCP` к `IP_малины:порт`**, где порт — тот же, что на Pi для видео (часто **`5000`**, если `send --listen --port 5000`).
2. Дальше в потоке идут **кадры подряд**:
   - **4 байта** — длина следующего JPEG, **big-endian** (`uint32`, сеть / network byte order).
   - затем ровно **`length` байт** — один полноценный **JPEG** (стандартный файл‑кадр: SOI `FF D8` … EOI `FF D9`).

Разрешение, FPS и «качество» JPEG задаются **на Raspberry Pi** (`--width`, `--height`, `--fps`, `--jpeg-quality`). На ПК вы только **декодируете JPEG** — любой декодер подходит (OpenCV `imdecode`, WIC, GDI+, Skia, браузер через преобразование и т.д.). Размер каждого кадра в байтах **разный** (VBR JPEG).

Минимальный цикл приёма (Python):

```python
import socket
import struct

HOST = "10.42.0.1"   # IP Pi в вашей сети
VIDEO_PORT = 5000

def recv_exact(sock: socket.socket, n: int) -> bytes:
    chunks = []
    left = n
    while left > 0:
        part = sock.recv(left)
        if not part:
            raise EOFError("конец потока")
        chunks.append(part)
        left -= len(part)
    return b"".join(chunks)

with socket.create_connection((HOST, VIDEO_PORT), timeout=10) as s:
    while True:
        hdr = recv_exact(s, 4)
        (length,) = struct.unpack(">I", hdr)
        jpeg_bytes = recv_exact(s, length)
        # jpeg_bytes — один кадр; отдайте в свой декодер / пайплайн отображения
```

На стороне Pi отправка задана в `rpi_tools/camera_stream.py`: `struct.pack(">I", len(payload))` + байты JPEG.

Если ваш текущий приёмник ждёт **HTTP** или **multipart MJPEG**, его нужно заменить или добавить **прокси** на ПК: один TCP‑клиент по протоколу выше → декодирование → уже ваш UI.

## 2. Отдельное TCP‑соединение только под команды

Откройте **один долгоживущий** TCP‑клиент на `IP:control` (например `192.168.1.50:5001`).

- Кодировка: **UTF‑8**.
- Формат: **одна логическая команда = одна строка, в конце символ перевода строки `\n`** (как «Serial Monitor» с включённым newline).
- Ответ от Pi: **одна строка JSON на каждую отправленную строку** (удобно читать построчно).

Пример ответа:

```json
{"ok": true, "reply": "OK\r\n"}
```

При ошибке:

```json
{"ok": false, "error": "..."}
```

Поле **`reply`** — это сырой ответ прошивки Romeo (может быть пустым).

### Опрос АЦП и напряжение аккумулятора (~20 В через делитель)

Команда **`A0`** … **`A5`** или JSON **`{"action":"adc_read"}`** (по умолчанию канал **A1** на Pi, см. `ROMEO_ADC_DEFAULT_CHANNEL`) / **`{"action":"adc_read","ch":n}`** возвращают в **`reply`** строку вида `A1 512 2502` (сырой код и милливольты на входе АЦП).

Дополнительно в том же JSON при успехе Pi подставляет:

- **`adc_raw`**, **`adc_pin_mv`** — как в прошивке (millivolts считаются в скетче, часто из **AVCC ≈ 5 В**);
- **`adc_pin_mv_cal`** — милливольты на пине после поправки **`ROMEO_ADC_FIRMWARE_MV_SCALE`** в `rpi_tools/config.py` / переменной окружения (ближе к мультиметру);
- **`battery_v`** — расчётное напряжение на аккумуляторе (**вольты**), если настроен делитель (по умолчанию **47 kΩ** сверху к «плюсу», **10 kΩ** с узла АЦП на землю: \(U_{акб} = U_{пин\_cal} \cdot (47+10)/10\)).

Если мультиметр на выводе АЦП показывает **другое**, чем поле **`adc_pin_mv`** (например на пине **3.01 В**, а в строке **4648 mV**), задайте масштаб один раз — отношение правды к числу из UART:

```bash
export ROMEO_ADC_FIRMWARE_MV_SCALE=0.6476   # пример: 3010 / 4648
```

После этого **`adc_pin_mv_cal`** и **`battery_v`** будут согласованы с измерением на пине. Долгосрочно можно поправить **`kAdcReferenceMv`** в прошивке под реальный AVCC.

На UI ПК для индикатора заряда используйте **`battery_v`**, а не «сырой» код АЦП.

Пример ответа:

```json
{"ok": true, "reply": "A0 585 2860\r\n", "adc_ch": 0, "adc_raw": 585, "adc_pin_mv": 2860, "adc_pin_mv_cal": 1852, "battery_v": 10.56}
```

**Калибровка опоры АЦП на МК** (команды прошивки `VCC`, `VREF`, `VREF <mВ>`, `VREF AUTO`): можно слать **текстом** в тот же TCP-порт или JSON:

| Действие | Пример JSON |
|----------|----------------|
| Измерить AVCC по bandgap и принять как опору | `{"action":"adc_vcc"}` |
| Показать текущий VREF | `{"action":"adc_vref"}` |
| Задать VREF вручную (500..7000 мВ) | `{"action":"adc_vref_set","mv":4980}` |
| Как VCC (авто) | `{"action":"adc_vref_auto"}` |

В ответе NDJSON при строках `VCC …` / `VREF …` добавляются поля **`vcc_mv`** / **`vref_mv`**.

На Raspberry Pi с USB: `python3 stream_camera.py adc-cal vcc` · `adc-cal vref` · `adc-cal vref --set 4980` · `adc-cal vref-auto` (по умолчанию `--read-timeout 5` для **VCC**).

## 3. Что слать на Pi

### 3.1. Текстом — как в Serial к Romeo

Любая строка из справки прошивки, например:

```text
MF
MB
MS
TL
TR
TANK 200 -200
PANL
TILTU
PL
PR
TU
TD
TS
HOME
```

Каждая строка заканчивается `\n`.

### 3.2. JSON — удобно из кнопок и стрелок

Одна строка JSON + `\n`:

| Действие | Пример строки (отправить как одну линию + `\n`) |
|----------|--------------------------------------------------|
| Вперёд / назад / стоп | `{"action":"drive","dir":"forward"}` / `"back"` / `"stop"` |
| Разворот на месте | `{"action":"drive","dir":"left"}` → **TANK −mag mag**, `"right"` → **TANK mag −mag** (mag ≈ `--romeo-tank-speed`×0.5 на Pi, см. `ROMEO_PIVOT_TANK_SCALE` в `rpi_tools/config.py`). Текстом по-прежнему можно слать **TL**/**TR**. |
| Две гусеницы | `{"action":"tank","left":200,"right":-200}` или ключи `l` / `r` |
| Башня (шаг) | `{"action":"turret","dir":"left","step":1}` — на Pi шаг умножается на **0.5** (`ROMEO_TURRET_STEP_SCALE`); мелкий шаг + частые повторы = плавно |
| Башня (как в прошивке) | `{"action":"turret","dir":"up"}` — без `step` (шаг по умолчанию в прошивке, часто крупный) |
| Угол PAN/TILT | `{"action":"pan","deg":45}` / `{"action":"tilt","deg":20}` / `{"action":"aim","pan":45,"tilt":20}` |
| **Плавная башня по направлению** | `{"action":"turret_smooth","dir":"left","v":20}` → **PL** с скоростью **v×0.5** на Pi (`ROMEO_TURRET_VEL_SCALE`); без `v` — как в прошивке |
| **Плавный поворот/наклон со знаком (град/с)** | `{"action":"pan_vel","v":12}` → **PANV**, `{"action":"tilt_vel","v":-8}` → **TILTV** |
| Обе оси скоростью | `{"action":"turret_vel","pan":10,"tilt":3}` → **TURRETV**; можно только `pan` или только `tilt` |
| Стоп плавного хода | `{"action":"turret_stop"}` → **TS** (синоним **TSTOP** в прошивке) |
| Домой | `{"action":"home"}` |
| Произвольная команда | `{"romeo":"FIRE/IR"}` |
| АЦП канал по умолчанию (A1) | `{"action":"adc_read"}` или `"ch":3` |
| Калибровка VCC / VREF | `{"action":"adc_vcc"}`, `adc_vref`, `adc_vref_set` + `"mv"`, `adc_vref_auto` |

На Pi можно задать **`--romeo-turret-step 2`**: тогда JSON `turret` **без** поля `step` превратится в `PANL 2` / `TILTU 2` и т.д. (мельче, чем встроенный крупный шаг прошивки).

Если в прошивке есть **PL/PR/TU/TD** и **TS**, для стрелок удобнее **`turret_smooth`** (при **keyup** — **`turret_stop`** → **TS**). Альтернатива: **PANV** / **TILTV** / **TURRETV** и снова **`turret_stop`**.

### 3.3. Почему башня «дёргается» и как сделать плавно

Прошивка для `PANL` / `TILTU` без аргумента использует **свой** шаг (часто большой) — при каждом срабатывании кнопки на ПК серва перескакивает заметно.

**Сделайте на ПК один из подходов:**

1. **Команды PL/PR/TU/TD:** при удержании — `{"action":"turret_smooth","dir":"left"}` (опционально `"v":20`), при отпускании — **`turret_stop`** (**TS**).
2. **Или PANV/TILTV** с нужным знаком **v**, при отпускании — **`turret_stop`**.
3. **Мелкий шаг + чаще:** раз в **30–50 ms**  
   `{"action":"turret","dir":"left","step":1}` (или `step:2`).
4. **Параметр на Pi:** `--romeo-turret-step 2` для пошагового режима без явного `step` в JSON.

Не полагайтесь только на autorepeat клавиатуры: лучше **turret_smooth** на keydown/keyup или таймер для пошагового режима.

Точное соответствие строк прошивке — в `rpi_tools/romeo_control_server.py`.

### 3.4. Рывки и у моторов, и у серв (задержки по цепочке ПК → Pi → USB)

На **Raspberry Pi** раньше на **каждую** команду открывался и закрывался USB‑Serial к Romeo — на CDC это даёт заметные паузы и «дёрганое» управление. Сейчас порт **держится открытым** между командами (`rpi_tools/romeo_usb.py`), плюс на сокете управления включён **TCP_NODELAY** и укорочено ожидание конца ответа прошивки (`romeo_control_server`).

На **ПК** по-прежнему важно:

- не слать команды **реже**, чем нужно для плавности (для **TANK** / **MF** держите поток обновлений или не отпускайте «газ» до одного импульса);
- для башни — **`turret_smooth`** + **`turret_stop`**, малый **`step`** по таймеру, а не редкие крупные **PANL** без аргумента;
- один **долгоживущий** TCP‑клиент на порт **5001**, без переподключения на каждое нажатие.

После обновления кода на Pi перезапустите `camstream` / `stream_camera`.

### 3.5. Рывки только у серв, моторы нормальные

Тогда **PWM-рампа для гусениц не нужна** — имеет смысл только башня.

1. **На ПК:** предпочтительно **`turret_smooth`** + **`turret_stop`** (→ **PL**…**TS**), либо **PANV/TILTV** + **`turret_stop`**. Иначе — малый **`step`** и таймер (§3.3).
2. **В прошивке** сглаживание внутри PL/PANV — тогда не нужен спам `PANL`.

## 4. Как привязать клавиатуру в приложении на ПК

Логика только на стороне клиента:

1. **Гусеницы (вперёд / назад / вбок):** на **keydown** один раз шлите команду (**`MF`**, **`MB`**, **`TL`**, **`TR`** или JSON `drive`; JSON **left/right** на Pi превращается в **TANK** с половинным модулем от `--romeo-tank-speed`), на **keyup** — **`MS`** / `drive stop`. Не вешайте отправку на **autorepeat** клавиатуры при удержании: это даёт десятки одинаковых строк в секунду, каждая ждёт ответа по USB и легко «просаживает» и управление, и видео на слабом клиенте. На Pi **повтор той же строки**, что уже ушла на USB, по этому TCP **не дублируется**, пока не придёт другая команда — но правильный паттерн на ПК всё равно **один импульс на зажатие + стоп на отпускание**.
2. **Башня:** при удержании стрелок не шлите JSON/`turret_smooth` на **каждый autorepeat** — либо **keydown → одна** команда плавности (**PL**/JSON), **keyup → TS**, либо мелкий **`turret`** `step` по **своему таймеру** (30–50 мс), не по частоте клавиатуры. На Pi повтор **той же строки** (**PL**, **PR**, **PANV**, …) без смены команды на USB не уходит; **PANL 1** / **PANL 2** с числом намеренно **не** фильтруются (каждый шаг важен).
3. При **keyup** башни — **`turret_stop`** (**TS**).
4. При **keyup** моторов — **`MS`** или `{"action":"drive","dir":"stop"}`.
5. Текстом: **`PL`**, **`TD 15`**, **`TS`**, **`TSTOP`** — тоже можно (см. §3.1).

Пример соответствия (можно поменять под себя):

- Вперёд / назад — `drive` forward / back (**keydown** один раз, **keyup** `stop`; без autorepeat).
- Влево / вправо на месте — `drive` left / right (на Pi → **TANK** с mag≈`romeo-tank-speed`×0.5; явные **TL**/**TR** в тексте без масштаба).
- Стрелки — **`turret_smooth`** + **`turret_stop`**, либо PANV/TILTV, либо **`turret`** с `"step":1` и таймер / `--romeo-turret-step` на Pi.

## 5. Минимальный пример (Python), только управление

```python
import socket
import json

HOST = "192.168.1.50"  # IP Raspberry Pi
CONTROL_PORT = 5001

def send_line(sock: socket.socket, line: str) -> dict:
    sock.sendall((line.rstrip("\n") + "\n").encode("utf-8"))
    buf = b""
    while b"\n" not in buf:
        chunk = sock.recv(4096)
        if not chunk:
            raise ConnectionError("соединение закрыто")
        buf += chunk
    first, _, rest = buf.partition(b"\n")
    return json.loads(first.decode("utf-8"))

with socket.create_connection((HOST, CONTROL_PORT), timeout=5) as s:
    r = send_line(s, '{"action":"drive","dir":"forward"}')
    print(r)
    r = send_line(s, "MS")
    print(r)
```

В реальном UI соединение **`with`** держите открытым всё время окна управления, а не на каждое нажатие.

## 6. Видео подвисает или дёргается, когда нажимаете клавиши

Чаще всего виноват **не** Raspberry Pi, а то, что на **ПК один поток** и занят и обработкой клавиш, и чтением TCP с видео.

1. **Отдельный поток (или async)** только под приём видео: бесконечный цикл `recv_exact(4)` → `recv_exact(length)` → положить JPEG в очередь → UI‑поток только декодирует и рисует последний кадр. Пока UI обрабатывает ввод, сокет **продолжают дренировать** в фоне — иначе буфер TCP на Pi заполняется, `sendall` блокирует кодирование, картинка «стопорится».

2. **Управление** держите во **втором** соединении (`control`), как в §2 — не смешивайте с циклом видео в одном синхронном обработчике «keydown → отправить команду → ждать ответ → только потом recv видео».

3. На стороне **Pi** (начиная с текущей версии репозитория) по умолчанию включена **`--jpeg-tcp-queue`** (очередь из нескольких кадров и отдельный поток отправки): кодер реже блокируется, если приёмник читает с паузами. Для записи без пропусков кадров по проводу можно задать **`--jpeg-tcp-queue 0`**.

4. **Пример для ПК:** в репозитории **`examples/pc_parallel_client.py`** — поток **только** читает видео TCP, управление — отдельное соединение (интерактив или режим **`--stress`**). Скопируйте файл на удалённый ПК:  
   `python3 examples/pc_parallel_client.py --host IP_малины`  
   Для окна: **`--window`** (нужны `opencv-python-headless`, `numpy`). Ту же идею перенесите в своё приложение (Unity/Qt/Electron).

5. **Если в логах ПК видео ~30 кадр/с, но иногда падает до ~20–28 при всплесках команд** — часто виноват не Pi, а **декод JPEG** (`imdecode`) и GIL: поток читает TCP хорошо, но декод на каждом кадре в том же процессе конкурирует с очередью Romeo. Решение: один поток **только recv** и очередь сырых JPEG с политикой «оставить последний» (`maxsize=1`), декод и UI — отдельно и не чаще, чем нужно экрану. Спам **INFO**-логов на каждую команду тоже замедляет — детали в **DEBUG**.

## 7. Частые проблемы

- **Держу любую кнопку (ход, башня) — видео лагает** — типично **autorepeat** + обработка всего в одном потоке на ПК. Паттерн **keydown / keyup** (§4), видео — **отдельный поток** (§6). На Pi подряд идущие **одинаковые** строки команд (**PL**, **PANV**, **TANK**, …) на USB не повторяются, пока не сменится команда; пошаговые **PANL n** / абсолютные **PAN**/**TILT** не фильтруются.
- **Нет поля `control` в discovery** — на Pi запуск без `--romeo-control-port 0` и с `--listen`; либо задайте порт вручную (**5001** по умолчанию).
- **Таймауты** — не блокируйте UI поток; отправку лучше ставить в очередь или отдельный поток.
- **Один USB Romeo** — Pi сериализует команды; два клиента одновременно могут мешать друг другу — проще один TCP‑клиент управления с ПК.

Этого достаточно, чтобы реализовать вторую половину на любом стеке (Electron, Qt, Unity, браузер через нативный шлюз и т.д.): главное — TCP, строки с `\n` и разбор JSON‑ответов построчно.
